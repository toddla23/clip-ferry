# 06. 결정 기록

이미 내린 결정은 이유와 함께 남긴다. 뒤집으려면 사용자와 합의 후 새 항목으로 기록하고 이전 항목에 `→ D-0xx로 대체`를 적는다.

## 결정

### D-001. 서버는 내용과 내역을 저장하지 않는다
- 메시지 큐·오프라인 보관함 없음. 받을 기기가 없으면 버린다.
- 이유: 서비스의 핵심 약속. 서버가 털려도 잃을 게 없어야 한다.
- 결과: 오프라인 기기 전달은 푸시(텍스트) 또는 보낸 기기의 재전송(6절)으로만 한다.

### D-002. 계정 없이 그룹 키 기반으로 운영한다 → D-019로 대체 (계정 부분만)
- 이메일·로그인 없음. 그룹은 기기들이 공유하는 비밀로만 존재.
- 결과: 모든 기기를 잃으면 복구 불가 → 새 그룹을 만든다. 사용자에게 명확히 안내.
- 2026-11-06: "로그인 없음"은 D-019로 대체. "그룹은 기기들이 공유하는 그룹 키로 존재하고, 모든 기기를 잃으면 새 그룹"은 그대로다.

### D-003. 채널 ID를 능력(capability)으로 쓴다
- 릴레이는 구성원 목록을 모르고, 추측 불가능한 `channel_id`를 아는 연결끼리 중계한다.
- 이유: 릴레이에 상태를 두지 않으면서 무작위 접근을 막는다. 키 회전 시 채널도 바뀌어 제거된 기기가 자연히 차단된다.
- 한계: 채널 ID를 아는 비구성원(제거 전 기기)은 이전 채널의 암호문을 볼 수 있지만 새 에포크 키는 모른다.

### D-004. 공통 코어는 Rust
- 암호·프로토콜 코드를 한 벌만 유지. UniFFI로 Kotlin/Swift 바인딩. 데스크톱(Tauri)·릴레이와 언어 통일.

### D-005. 모바일 셸은 네이티브 (Kotlin / Swift)
- 이 앱의 핵심 UX(타일, 포그라운드 서비스, App Intents, 각종 Extension)가 전부 OS 고유 기능이라 크로스플랫폼 UI의 이점이 작다.

### D-006. 데스크톱은 Tauri 2 + React + TypeScript
- 가벼운 상주 트레이 앱, 코어를 Rust에서 바로 호출. React는 자료·예제가 가장 많아서 선택.

### D-007. 푸시 토큰은 로스터에 담고, 보내는 기기가 요청마다 릴레이에 넘긴다
- 릴레이는 토큰을 저장하지 않는다. 받을 기기가 오프라인일 때만 그 요청에 실린 토큰으로 푸시하고 잊는다.
- 한계: 전송 순간 릴레이는 토큰을 본다. 푸시 남용은 속도 제한으로 막는다(F27).

### D-008. 모든 기기는 동등하다 (관리자 기기 없음)
- 어느 기기든 추가·제거·이름 변경 가능. 충돌은 로스터 version → 해시 순으로 해소.
- 이유: 개인 기기 묶음에서 권한 계층은 불필요한 복잡도.

### D-009. MLS(RFC 9420)는 쓰지 않는다
- 개인 기기 수(수 대~수십 대)에서는 "기기별 래핑 + 에포크" 방식으로 충분하다. 팀/가족 공유를 하게 되면 재검토.

### D-010. CLI는 개발·검증 도구이며 예외적 동작을 허용한다
- CLI는 비밀을 프로필 폴더 파일에 저장(`FileSecretStore`)하고, 받은 이미지를 `./received/`에 저장할 수 있다.
- 시작 시 "개발용" 경고를 출력한다. 이 동작들은 앱(셸)에 절대 옮기지 않는다.

### D-011. 초대 텍스트 코드는 v1에서 32바이트 비밀 전체(base32 52자)
- PAKE 없이도 안전한 가장 단순한 방식. 입력 불편은 QR이 주 경로라 감수. 짧은 코드는 O-02.

### D-012. 릴레이 프레임 한도는 2 MiB
- 텍스트 최대 1 MiB를 한 봉투에 담아야 하는데 기존 한도 512 KiB로는 들어가지 않는다. 텍스트를 쪼개는 새 메시지를 만들기보다 프레임 한도를 올렸다(이미지는 256 KiB 청크라 영향 없음).
- 연결당 분당 64 MiB·초당 50프레임 제한은 그대로다. 푸시 페이로드 3,000바이트 제한과도 무관(큰 봉투는 "도착 알림"만 보낸다).
- 되돌리려면: 텍스트도 이미지처럼 청크로 보내는 방식(F12 이후 검토)으로 바꾸고 한도를 다시 낮춘다.

### D-013. 이전 에포크 채널의 메시지는 현재 구성원이 보낸 것만 받는다
- 키 회전 뒤에도 30일 동안 옛 채널을 듣는데, 제거된 기기는 옛 키를 그대로 갖고 있다. 옛 채널로 온 메시지는 보낸 기기가 지금 로스터에 있을 때만 처리해, 제거된 기기가 계속 메시지를 밀어 넣지 못하게 한다.
- 대가: 돌아온 기기의 `EpochQuery`만 예외로 응답해야 해서 로직이 한 군데 더 필요하다.

### D-014. 릴레이는 먼저 집 라즈베리파이(Tailscale)에 올려 시험하고, 이후 클라우드로 옮긴다
- 개인 용도 검증 단계라 비용과 계정 없이 시작한다. Pi 5(64비트 Debian)에 Docker로 올리고, 같은 tailnet의 기기끼리 `ws://<Tailscale IP>:8787`로 접속한다. 포트는 Tailscale IP에만 바인드한다.
- 인증서는 나중에 받는다. 그때까지 평문 `ws://`를 쓰되 Tailscale 구간이 WireGuard로 암호화된다. 클라이언트는 이미 `wss://`를 지원한다.
- 이유: 서버 호스팅·도메인 결정(O-03, O-04)을 미루고도 서로 다른 네트워크 동작을 시험할 수 있다. 릴레이 주소는 설정값이라 이후 이전이 쉽다.
- 한계: 폰도 Tailscale이 켜져 있어야 한다. 모바일 OS는 평문 `ws://`를 막는 경우가 많다고 보았으나, F15 실기기 시험에서 안드로이드는 코어(Rust) 소켓의 `ws://`를 막지 않았다(`ws://<LAN IP>:8787`로 `연결됨`). iOS는 F21에서 따로 확인한다.
- 정책(F15 시험 뒤): 개발·시험에는 `ws://`를 허용한다. 안드로이드가 막아 주지 않으므로, 정식 배포에서 `wss://`만 받을지는 앱이 직접 막아야 한다. O-03(도메인·기본 주소)과 함께 정한다.

### D-015. UniFFI 바인딩은 코어가 아니라 별도 `ffi/` 크레이트에 둔다
- 코어(`clip-ferry-core`)는 데스크톱·릴레이·CLI도 쓴다. 거기에 UniFFI 매크로를 넣으면 그들의 빌드와 의존성까지 바뀐다. 모바일 셸용 `clip-ferry-ffi`가 코어를 감싸며, 비동기 세션은 안에서 tokio 런타임으로 돌리고 셸에는 동기 호출과 콜백만 노출한다.
- Kotlin 바인딩은 `uniffi-bindgen`의 라이브러리 모드로 `.so`에서 생성하고 git에는 넣지 않는다(빌드 스크립트가 만든다).
- 한계: 코어 공개 API가 늘면 `ffi/`에도 같은 모양의 래퍼를 더해야 한다. 대신 래퍼가 오류·타입을 셸에 맞게 단순하게 만든다.

### D-016. 앱이 꺼진 iOS로 이미지·긴 텍스트는 보낸 기기가 다시 보낸다 (O-01 → 기본안 A, 2026-11-05 사용자 결정)
- 서버 무저장(D-001)을 그대로 지킨다. 알림을 누르면 아이폰이 `ResendRequest`를 보낸 기기에게만 게시하고, 보낸 기기가 메모리에 10분 들고 있던 마지막 클립을 그 기기에게만 다시 보낸다(03-protocol 6절).
- 한계: 보낸 기기가 그때 꺼져 있으면 못 받는다("보낸 기기가 오프라인입니다").

### D-017. F20(FCM 푸시)은 보류한다 (2026-11-05 사용자 결정)
- Android는 포그라운드 서비스(F15)로 연결을 유지해 앱 화면이 꺼져 있어도 받는다. Firebase 프로젝트·서비스 계정·릴레이 → Google 요청을 들이는 비용이 더 크다고 보았다.
- 한계: 강제 종료나 제조사 절전으로 서비스가 죽으면 앱을 다시 열 때까지 못 받는다.
- 릴레이 푸시 게이트웨이는 iOS(F22, APNs)용으로 만들기 때문에 나중에 FCM을 붙일 자리는 남는다.

### D-018. 배포 파일은 GitHub Actions가 만들어 GitHub Releases에 올린다 (2026-11-05)
- `v*` 태그 푸시 → Windows NSIS 설치 파일, macOS 유니버설 `.dmg`, Linux `.deb`·`.AppImage`, Android 서명 `.apk`. 절차는 `docs/07-release.md`.
- Android 배포 서명 키는 저장소 밖에 두고 GitHub Secrets(`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`)로만 CI에 준다. 업데이트가 같은 키끼리만 되므로 키는 바꾸지 않는다.
- 한계: 데스크톱 코드 서명·공증과 자동 업데이트는 없다(F31 후속).

### D-019. 구글 로그인(필수)과 계정 서버를 둔다. 클립보드 내용의 종단간 암호화는 그대로 (2026-11-06 사용자 결정, D-002 대체)
- 목적(사용자 답): 남용 방지, 사용자 관리·통계, 기기 연결을 쉽게, 유료화·사용량 제한의 바탕.
- 로그인은 **필수**다. 앱은 로그인해야 쓸 수 있고, 릴레이는 계정 서버가 발급한 접속 토큰이 있는 연결만 받는다.
- 서버에 저장하는 것: 구글 계정 기본정보(구글 ID `sub`, 이메일, 이름, 프로필 사진 URL, 가입 시각), 계정에 묶인 기기 목록(기기 이름·플랫폼·마지막 접속 시각), 사용 기록(전송 횟수·바이트·시각 — **내용 없이**).
- 저장하지 않는 것: 클립보드 내용·내역, 그룹 키, 기기 개인키. 그룹 키는 지금처럼 기기에만 있고 기기끼리 래핑해 넘긴다(D-001, 03-protocol 1·4절 그대로). 서버가 털려도 클립보드 내용은 안전하다.
- 새 기기는 여전히 기존 기기의 승인으로만 그룹에 들어간다(원칙 4). 계정은 "누가 승인 요청을 보낼 수 있는지"를 좁히고 QR·코드를 생략하게 해 줄 뿐, 계정 서버가 그룹 키를 줄 수는 없다.
- 구성: 새 `account/` 서버(Rust axum + MariaDB — 2026-11-06 사용자 결정, `sqlx`의 MySQL 드라이버로 접속. 공식 이미지가 arm64를 지원해 Pi에도 올린다). 릴레이는 DB를 보지 않고 접속 토큰의 서명만 확인한다(릴레이는 계속 가볍게).
- 따라오는 것:
  - App Store 심사 지침 4.8(제3자 로그인을 쓰면 이메일을 가릴 수 있는 로그인을 동등하게 함께 제공) 때문에 **Sign in with Apple**도 제공한다(2026-11-06 사용자 확인). 계정은 구글·Apple 신원 둘 다 가질 수 있다. iOS는 F36에서 네이티브로, 데스크톱·Android는 Apple에 등록할 https 도메인이 필요해 F41(O-03 뒤)에서 웹 방식으로 붙인다. 그 전까지 Apple로 가입한 계정은 iOS에서만 로그인된다.
  - 앱 안 **계정 삭제**(App Store·Play 요구)와 **개인정보처리방침** 페이지.
  - 개발·시험은 Pi + Tailscale(D-014)에서 한다(2026-11-06 사용자 결정). 계정 서버·MariaDB도 Pi의 Docker에 올리고 `*.ts.net` 주소로 접속한다. 구글 OAuth 동의 화면은 "테스트" 상태(테스트 사용자 100명까지)로 두면 도메인·방침 URL 없이 된다.
  - 공개 서버·도메인(O-03·O-04)은 기능이 다 만들어진 뒤 **공개 배포 전**에 정한다(F40). 동의 화면 "프로덕션" 전환·구글 검수, 스토어 제출이 이때다.
  - 원칙 3·7(01-overview)을 고쳤다. 주장할 수 있는 것은 "서버는 클립보드 내용과 내역을 저장하지 않고 볼 수도 없다"까지다. 서버는 계정 정보와 사용량(크기·횟수·시각), IP를 안다.
- 유료화(요금제·결제)는 이번 결정 범위 밖이다. 계정과 사용량 집계를 깔아 두고, 착수 전에 따로 합의한다.
- 한계: 구글(또는 Apple) 계정 없이는 쓸 수 없다. 서버에 개인정보가 생기므로 유출 대비(최소 수집, 접근 통제, 삭제)가 운영 책임이 된다.

### D-020. 데스크톱 구글 로그인의 코드 교환은 계정 서버가 한다 (2026-11-06, F34)
- 데스크톱 앱은 구글 "데스크톱 앱" 클라이언트로 시스템 브라우저 + 루프백(`http://127.0.0.1:<임의 포트>/`) + PKCE(S256) + `state`로 인가 코드를 받는다(RFC 8252). 앱 안의 웹뷰로는 로그인하지 않는다(구글이 막는다).
- 구글은 데스크톱 클라이언트에도 코드 교환 때 클라이언트 보안 비밀을 요구한다. 그 값을 앱(공개 저장소·배포 파일)에 넣지 않고, 앱은 코드와 `code_verifier`를 계정 서버 `POST /v1/auth/google/code`로 넘기고 계정 서버가 구글과 교환한다. 받은 ID 토큰은 다른 경로와 똑같이 검증한다(`aud`에 데스크톱 클라이언트 ID).
- 계정 서버는 돌아올 주소가 `http://127.0.0.1:<포트>`일 때만 교환해 준다(다른 곳으로 받은 코드를 대신 바꿔 주지 않게). 코드는 PKCE 검증자 없이는 쓸 수 없다.
- 데스크톱 클라이언트 ID는 앱에 넣지 않고 계정 서버가 알려 준다(`GET /v1/auth/google/desktop`). 그래서 서버를 옮겨도(F40) 앱을 다시 빌드할 필요가 없다.
- 갱신 토큰은 OS 보안 저장소(keyring, 항목 `account/session`), 접속 토큰은 메모리에만 둔다. 갱신은 한 번에 하나씩(재사용으로 보이면 계정의 모든 로그인이 끊긴다).
- 한계: 로그인할 때 계정 서버가 구글에 닿아야 한다(로그인 뒤 갱신은 계정 서버만).

### D-021. Android 구글 로그인은 Credential Manager로 ID 토큰만 받고, 계정 처리는 `ffi`가 한다 (2026-11-07, F35)
- 셸은 Credential Manager의 `GetSignInWithGoogleOption`(시스템 구글 계정 선택 창)으로 ID 토큰을 받는다. `serverClientId`는 "웹 애플리케이션" 클라이언트 ID이고, 받은 토큰의 `aud`도 그 값이라 계정 서버의 기존 `POST /v1/auth/google`이 그대로 검증한다. 구글 비밀값은 앱에 없다.
- 웹 클라이언트 ID는 앱에 넣지 않고 계정 서버가 알려 준다(`GET /v1/auth/google/android`, 기본은 `CF_ACCOUNT_GOOGLE_CLIENT_IDS`의 첫 번째). D-020과 같은 이유(서버를 옮겨도 앱을 다시 빌드하지 않음).
- 구글은 같은 프로젝트에 "Android" 클라이언트(패키지 `app.clipferry.android` + 서명 인증서 SHA-1)가 있을 때만 토큰을 준다. 서명 키마다(디버그·배포) 하나씩 만든다. 그 클라이언트 ID는 어디에도 설정하지 않는다.
- 갱신 토큰 보관·한 번에 하나씩 갱신·거절 시 지우기·로그아웃·기기 등록은 `ffi/src/account.rs`에서 한다(Kotlin에는 HTTP·토큰 로직이 없다). 규칙은 데스크톱 `account.rs`(D-020)와 같다.
- 한계: 같은 규칙이 데스크톱과 `ffi`에 따로 있다(코드 두 벌). 코어 크레이트에 HTTP 클라이언트를 넣지 않으려고 그렇게 했다. iOS(F36)도 `ffi`를 쓰므로 세 번째 벌은 생기지 않는다. 구글 Play 서비스가 없는 기기에서는 로그인할 수 없다.

### D-022. 계정 연결은 서버 서명 확인서 + 봉인 후 공개 SAS로 한다 (2026-11-08, F37)
- 같은 계정의 새 기기는 계정 채널(`HKDF(user_id)`)에 계정 서버가 서명한 참여 확인서(공개키·이름·계정·만료)를 올린다. 기존 기기는 `GET /v1/keys`의 공개키로 확인하므로 다른 계정의 기기는 요청을 보낼 수 없다.
- 초대 비밀이 서버를 지나므로 4.2의 SAS(비밀 + 두 서명 공개키)로는 부족하다. 비밀을 아는 서버가 한쪽 키를 본 뒤 숫자가 같아지는 가짜 키를 100만 번 안에 찾을 수 있다. 그래서 새 기기가 키와 nonce의 해시를 먼저 보내고(봉인), 기존 기기의 키·nonce를 받은 뒤 공개한다. SAS에 두 nonce와 네 공개키가 들어간다(블루투스 숫자 비교와 같은 원리). 사용자 결정(2026-11-08).
- 기존 기기 사용자는 요청에 `연결`을 누르고, 양쪽 숫자를 비교해 `승인`한다(두 번 누름). 요청만으로 자동 진행하지 않는다(같은 계정의 기기가 여럿이어도 사용자가 고른 하나만 응한다).
- 확인서 서명 키는 접속 토큰 키와 같다(키를 하나 더 관리하지 않으려고). 서명하는 바이트에 영역 문자열을 붙여 JWT와 섞이지 않게 한다.
- 계정 채널 ID는 계정 ID로 정해지므로 계정 ID를 아는 쪽은 그 채널에 게시할 수 있다(스팸은 확인서 확인에서 버려진다). 릴레이가 토큰의 계정과 채널을 맞춰 보게 하는 것은 하지 않았다(릴레이는 채널 의미를 모르게 둔다).
- 한계: 한쪽 앱이 예전 버전이면 이 경로를 쓸 수 없고 QR·코드로 한다. 모든 기기가 같은 계정에 로그인해 있어야 한다.

### D-023. 운영자 통계는 계정 서버의 `/admin` 페이지 + 구글 로그인 허용 목록으로 본다 (2026-11-09, F38)
- 운영자는 브라우저로 `/admin`을 열어 구글로 로그인한다. 계정 서버가 ID 토큰을 확인하고 이메일이 `CF_ACCOUNT_ADMIN_EMAILS`에 있으면 운영자 토큰(1시간)을 준다. 목록 밖은 403. 목록이 비면 경로 자체를 열지 않는다(404).
- 운영자 토큰은 접속 토큰과 같은 서명 키를 쓰되 대상(aud)이 `clip-ferry-admin`이다. 릴레이·`/v1`은 `clip-ferry-relay`만 받으므로 서로 쓸 수 없다. API는 요청마다 허용 목록을 다시 보므로 목록에서 빼면 바로 막힌다.
- 활성 사용자(DAU·MAU)는 "그날 한 번이라도 전송한 계정"으로 센다. 서버에 날마다 남는 활동 기록이 일별 사용량(`usage_daily`)뿐이라서다(기기의 마지막 접속은 마지막 값만 남는다). 날짜는 UTC 일.
- 보여 주는 것: 가입자 수, DAU·MAU, 플랫폼별 기기 수(등록·최근 30일 접속), 일별 활성·신규 가입·전송 수·바이트, 사용자별 이메일·이름·기기 목록·사용량. 클립보드 내용은 서버에 없으므로 볼 수 없다(D-019).
- 별도 관리 앱이나 다른 인증 수단(비밀번호·IP 제한)은 두지 않았다. 지금은 Tailscale 안에서만 열려 있고, 공개 배포(F40) 때 노출 범위를 다시 본다.

### D-024. 계정 삭제는 서버가 즉시·전부 지우고, 삭제는 홈페이지에서만 한다 (2026-11-09, F39)
- `DELETE /v1/me`(Bearer 접속 토큰)는 계정, 기기 목록, 갱신 토큰, 일별 사용량을 한 트랜잭션에서 바로 지운다(유예 기간 없음). 외래 키의 연쇄 삭제에 기대지 않고 표마다 지운다. 같은 요청이 다시 와도 204.
- 갱신 토큰이 모두 없어지므로 그 계정의 기기는 다음 갱신(최대 1시간) 때 로그아웃된다. 이미 발급된 접속 토큰은 만료까지 릴레이 접속에 쓰일 수 있다. 릴레이가 DB를 보지 않게 둔 설계(D-019)를 유지하려고 받아들인다. 그 사이에도 계정 API(`/v1/*`)는 계정이 없어 401이다.
- 같은 구글 계정으로 다시 로그인하면 새 계정 ID로 시작한다. 기기의 그룹 정보(그룹 키)는 서버에 없으므로 서버 삭제와 상관없이 기기에 남는다.
- **앱에는 계정 삭제 버튼·경로를 두지 않는다**(사용자 결정 2026-11-09). 처음에는 데스크톱·Android에 `계정 삭제`(확인 → 서버 삭제 → 이 기기 그룹 나가기)를 만들었으나 뺐다. 삭제는 나중에 만들 홈페이지에서 구글 로그인 뒤 하게 한다(F40).
  - 알려 둔 위험: App Store 지침 5.1.1(v)는 앱 안에서 삭제를 시작할 수 있어야 하고(웹 페이지로 보내는 버튼은 허용), Google Play는 앱 안 경로와 웹 링크를 둘 다 요구한다. 스토어에 내기 전에 다시 정해야 한다.
- 일별 사용량은 13개월(396일) 보관하고 매시간 정리 작업이 지운다. 계정·기기 목록은 계정을 지울 때까지 둔다.
- 개인정보처리방침은 `docs/privacy.md` 초안으로 두고, 운영 주체·문의처·시행일·호스팅·삭제 페이지 주소는 F40에서 채워 공개 URL에 게시한다.

### D-025. 공개 서버 1단계는 Azure for Students VM 한 대에 올린다 (2026-11-10 사용자 결정, O-04)
- 사용자가 Azure for Students 크레딧 $100을 갖고 있다. 학생 무료 VM(월 750시간) 한 대에 릴레이·계정 서버·MariaDB를 지금 Pi와 같은 docker compose로 올리고, 앞단 TLS는 `tailscale serve` 대신 Caddy(Let's Encrypt 자동)가 맡는다. 비교 근거는 `docs/08-hosting.md`.
- 리전은 **Japan East**(도쿄, 한국에서 왕복 약 30ms). 학생 구독은 정책으로 배포 지역이 5곳(`japaneast`·`malaysiawest`·`indonesiacentral`·`centralindia`·`indiasouthcentral`)뿐이고, 그 어디서도 학생 무료 VM 크기를 만들 수 없었다(2026-11-10). 그래서 **VM은 크레딧으로 내는 가장 작은 크기**로 만든다(월 $10~15 예상 → 크레딧으로 약 6~9개월). 개인정보처리방침의 서버 위치는 일본. CPU 종류는 상관없다. 이미지를 소스에서 빌드하고 기반 이미지가 x86·ARM을 모두 지원한다.
- 1단계는 도메인 없이 Azure가 주는 무료 이름(`<이름>.japaneast.cloudapp.azure.com`)으로 `wss://`·`https://`를 연다. 도메인(O-03)은 2단계에서 정한다.
- 한계·위험:
  - 크레딧이나 학생 자격이 끝나면 VM이 멈춘다. 종량제로 바꾸거나 옮겨야 하므로 DB 백업·복원 절차를 처음부터 둔다.
  - 학생 구독은 학습용 혜택이다. 유료화(O-05)나 다수 사용자 운영 전에는 일반 구독이나 다른 호스팅으로 옮길지 다시 본다.
  - 메모리 1GB라 서버에서 Rust 빌드는 하지 않는다.

### D-026. 앱은 계정 서버 주소만 내장하고, 릴레이 주소는 계정 서버가 알려 준다. 주소는 사용자에게 숨긴다 (2026-11-10 사용자 결정, F43)
- 도메인 없이 Azure 이름(`clipferry.japaneast.cloudapp.azure.com`)을 배포 빌드 기본값으로 넣는다(사용자 결정: 도메인은 사지 않고 이 이름을 쓴다).
- 릴레이 주소는 `GET /v1/config`로 받는다. 릴레이를 옮기거나 늘려도(F26) 앱을 다시 배포하지 않아도 된다. D-020·D-021(구글 클라이언트 ID를 서버가 알려 줌)과 같은 이유다.
- 사용자는 기본으로 서버 주소를 보지 않는다(사용자 요청). 입력 칸은 지우지 않고 숨긴다(제목 7번 누르기). 서버를 옮길 때 재설치 없이 주소를 바꿀 수 있는 마지막 길이고, 개발(디버그 빌드)에는 항상 보인다.
- 한계: 계정 서버 주소가 바뀌면(크레딧이 끝나 서버를 옮기는 등) 이미 설치한 앱은 숨은 칸에 새 주소를 넣거나 새 버전을 설치해야 한다. Azure 이름은 이 서버의 공용 IP 리소스에 묶여 있어 다른 곳으로 가져갈 수 없다. 공개 서비스(구글 동의 화면 프로덕션)로 가려면 결국 도메인이 필요하다(F40 2단계).

### D-027. 계정 하나당 그룹 하나, 다른 계정의 기기는 그룹에 넣지 않는다 (2026-11-10 사용자 결정, F44)
- 같은 계정의 두 기기가 각자 그룹을 만들어 서로 안 이어지는 일을 막는다(사용자 제안).
- 서버는 그룹 키를 모르므로(E2E) 강제는 앱이 한다: 계정 서버는 "이 계정에 그룹에 있는 기기가 있다"만 알고, 앱은 그때 `새 그룹 만들기`를 숨긴다.
- 승인할 기기가 하나도 남지 않은 경우의 탈출구는 앱 안의 `처음부터 다시 시작`(경고 + 두 번 확인)으로 한다(사용자 결정. 운영자가 관리자 페이지에서 지워 주는 안은 택하지 않음).
- 다른 계정 기기와 그룹을 같이 쓰지 않는다(사용자 결정). QR·코드 연결도 같은 계정 확인서를 요구한다.

## 열린 질문 (해당 기능 착수 전에 사용자에게 묻는다)

### O-01. 앱이 꺼진 iOS로 이미지 보내기 (F25 전까지) — 결정: 기본안 A (D-016)
- 기본안 A: 완전 무저장 유지 — 알림 탭 시 보낸 기기에 재전송 요청. 보낸 기기가 그때 켜져 있어야 함.
- 대안 B: 릴레이 메모리에 암호문을 짧은 TTL(예: 5분) 보관 후 전달 시 삭제. D-001 예외가 되므로 채택 시 D-001 갱신 필요.

### O-02. 짧은 페어링 코드 (예: 6자리 숫자 또는 단어 3개)
- 데스크톱 ↔ 데스크톱 페어링 편의. SPAKE2 계열 PAKE 크레이트 추가가 필요(허용 크레이트 변경). 필요 시 F10 이후 논의.

### O-03. 번들 ID · 도메인 · 기본 릴레이 주소
- 예: `app.clipferry.*`, `relay.clipferry.app`. F14(릴레이 배포), F15(Android), F21(iOS) 전에 확정.
- D-019로 계정 서버 주소(예: `api.clipferry.app`), 개인정보처리방침 URL, 구글 OAuth 동의 화면의 승인된 도메인도 필요하다. **공개 배포(F40) 전에 결정** (개발은 Pi의 `*.ts.net`).
- 번들 ID는 정했다(2026-11-05): Android `app.clipferry.android`, 데스크톱 `app.clipferry.desktop`, iOS `app.clipferry.ios`(확장은 그 아래), App Group·키체인 그룹 `group.app.clipferry`. 도메인·기본 릴레이 주소는 아직.

### O-04. 릴레이 호스팅 (F14 전) — 1단계는 D-014(Pi + Tailscale)로 결정, 클라우드는 이후
- 후보: Fly.io(관리 편함, WebSocket·TLS 기본 제공) / Hetzner VPS + Caddy(저렴, 직접 관리).
- D-019로 계정 서버와 MariaDB도 같이 올라가야 한다. M7 개발·시험은 Pi에서 하고 **공개 배포(F40) 전에 결정.**
- 후보 비교(2026-11-10 조사, 가격·지연·장단점): `docs/08-hosting.md`.
- **1단계 결정: D-025**(Azure for Students VM + Caddy, 2026-11-10). 유료화·다수 사용자 전에 다시 본다.

### O-05. 유료화 (M7 이후)
- 요금제·무료 한도·결제 수단(웹 결제 / 앱 내 결제 — 모바일은 스토어 규정)을 정한다. 계정·사용량 집계(F32·F33)가 바탕.
