# 04. 기능 명세

각 기능은 **사용자가 직접 실행해서 확인할 수 있는 단위**로 나눴다. 형식:

- **목표**: 이 기능이 끝나면 무엇이 되는가
- **선행**: 먼저 `완료`여야 하는 기능
- **범위 / 범위 밖**: 만들 것과 이번에 만들지 않을 것
- **완료 조건**: 전부 충족해야 `확인대기`로 올릴 수 있다
- **사용자 확인 방법**: 사용자가 실제로 해볼 절차와 기대 결과. 구현 중 명령어가 바뀌면 이 절을 고치고 보고에 반영한다

공통 완료 조건(모든 기능): `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` 통과, 관련 문서 갱신, `05-progress.md` 갱신.

CLI 명령 예시는 `cf` = `cargo run -q -p clip-ferry-cli --` 의 줄임이다.

# M1. 코어 · 릴레이 · CLI — "터미널 두 개로 암호화된 텍스트가 오간다"

## F01. 레포 스캐폴딩과 CI

- **목표**: 빈 워크스페이스가 빌드되고 CI가 돈다.
- **선행**: 없음
- **범위**: Cargo 워크스페이스(`core`, `relay`, `tools/cli`), 각 크레이트 빈 골격, `rust-toolchain.toml`(stable 고정), `.gitignore`, `README.md`, GitHub Actions(fmt, clippy, test — Linux/macOS/Windows), `proto/` 폴더와 빌드 스크립트 자리
- **범위 밖**: 실제 로직, 앱 프로젝트(apps/)
- **완료 조건**
  - [ ] `cargo build --workspace` 성공
  - [ ] `cf --version`, `cargo run -p clip-ferry-relay -- --version` 이 버전을 출력
  - [ ] CI 워크플로 파일이 있고 로컬에서 같은 명령들이 통과
- **사용자 확인 방법**
  1. `cargo test --workspace` → 실패 없이 끝남
  2. `cf --version` → `clip-ferry-cli 0.1.0`
  3. GitHub에 푸시 후 Actions 탭에서 세 OS 모두 초록색

## F02. 코어 암호 기본

- **목표**: 기기 키, 그룹 키, 파생값, 봉인/개봉, 기기 간 래핑이 테스트로 검증된다.
- **선행**: F01
- **범위**: `core/src/crypto` — `DeviceKeys`(생성·직렬화), `GroupKey`, HKDF 파생(`content_key`, `channel_id`, `device_tag`), AEAD seal/open(XChaCha20-Poly1305, aad 포함), `wrap_for`/`unwrap`, 비밀 타입 zeroize + 가려진 `Debug`. 03-protocol 1절 확정.
- **범위 밖**: protobuf, 네트워크
- **완료 조건**
  - [ ] 정상 왕복 테스트 (seal→open, wrap→unwrap)
  - [ ] 실패 테스트: 암호문 1비트 변조, aad 변경, 다른 키, 다른 수신자의 unwrap, 잘린 입력 → 모두 에러
  - [ ] 같은 입력으로 두 번 seal 하면 nonce·암호문이 다름
  - [ ] 파생값 고정 테스트 벡터(테스트 안에 하드코딩) 통과 — 나중에 다른 언어/버전과 비교 기준
  - [ ] 비밀 타입의 `{:?}` 출력에 키 바이트가 없음을 확인하는 테스트
- **사용자 확인 방법**
  1. `cargo test -p clip-ferry-core crypto -- --nocapture`
  2. 기대 결과: `tamper`, `wrong_key`, `wrong_aad`, `wrong_recipient`, `truncated`, `debug_redacted` 등의 이름이 들어간 테스트가 모두 `ok`

## F03. 메시지 포맷과 봉투

- **목표**: 페이로드를 직렬화·서명·봉인하고, 받는 쪽 검증 순서(03-protocol 2.2)가 동작한다.
- **선행**: F02
- **범위**: `proto/clip_ferry.proto` 작성(봉투·페이로드·컨트롤·페어링·릴레이 프레임 전부 정의), `prost-build`, `core/src/envelope`(서명, 봉인, 검증 파이프라인, 중복 목록, 시간 창)
- **범위 밖**: 이미지 조립(F12), 실제 전송
- **완료 조건**
  - [ ] 2.2의 검증 단계마다 실패 케이스 테스트 1개 이상 (모르는 에포크, 서명 위조, 로스터에 없는 발신자, 중복 msg_id, 시간 창 밖, epoch 불일치, 자기 메시지)
  - [ ] `proptest`로 임의 바이트 입력이 패닉 없이 에러로 끝남
  - [ ] 03-protocol 2절 `(초안)` 제거, proto와 문서 일치
- **사용자 확인 방법**
  1. `cargo test -p clip-ferry-core envelope`
  2. 기대 결과: 검증 단계별 테스트가 모두 `ok`, 퍼징 테스트 `ok`

## F04. 릴레이 서버 최소판 + 코어 전송 계층

- **목표**: 릴레이에 여러 클라이언트가 붙어 채널 단위로 바이트를 주고받고, 끊기면 자동 재연결한다.
- **선행**: F03
- **범위**: `relay`(axum WS, Subscribe/Unsubscribe/Publish/Ping, Deliver/Ack/Error/Presence/Hello, 크기·속도·구독 수·IP당 연결 제한, 디스크 쓰기 없음), `core/src/transport`(연결, 지수 백오프 재연결 1s→최대 60s, 재연결 시 재구독, 핑), CLI `debug` 서브커맨드(`debug sub <hex>`, `debug pub <hex> <문자열>`) — 암호화 없이 원시 바이트로 릴레이만 시험
- **범위 밖**: 푸시(F20), TLS 종단(F14에서 리버스 프록시), 다중 노드(F26)
- **완료 조건**
  - [ ] 통합 테스트: 같은 채널 두 클라이언트 전달 / 다른 채널 미전달 / 미구독 publish 거부 / 프레임 초과 `TOO_LARGE` / 속도 초과 `RATE_LIMITED` / 수신자 없을 때 `delivered=0`
  - [ ] 릴레이 재시작 후 클라이언트가 자동 재연결·재구독하는 테스트
  - [ ] 릴레이 코드에 파일 쓰기 API 사용이 없음 (`grep` 결과를 보고에 첨부)
- **사용자 확인 방법**
  1. 터미널 1: `cargo run -p clip-ferry-relay -- --listen 127.0.0.1:8787`
  2. 터미널 2: `cf debug sub 00` / 터미널 3: `cf debug pub 00 hello`
  3. 기대 결과: 터미널 2에 `hello` 출력, 터미널 3에 `delivered=1`
  4. 터미널 1을 Ctrl+C 후 다시 실행 → 터미널 2에 `reconnecting...` 뒤 `connected`, 이후 pub이 다시 도착

## F05. 그룹 생성과 로컬 상태

- **목표**: CLI 프로필이 기기 키·그룹을 만들고 재시작 후에도 유지한다.
- **선행**: F04
- **범위**: `core/src/store`(`SecretStore` 트레이트, 암호화된 `state.bin`), CLI `FileSecretStore`(개발용 경고 출력), `core/src/group`의 그룹 생성·로스터 기본, 공개 API `ClipFerry::open/create_group/devices`, CLI `--profile`, `cf init --name <이름>`, `cf group create`, `cf status`
- **범위 밖**: 페어링, 다른 기기
- **완료 조건**
  - [ ] 재시작 후 같은 device_id·채널로 접속
  - [ ] `state.bin` 변조 시 열기 실패 + 명확한 에러 메시지(내용 노출 없음) 테스트
  - [ ] `cf status`가 비밀값을 출력하지 않음 (device_id는 앞 4바이트 hex만)
- **사용자 확인 방법**
  1. `cf --profile a init --name laptop` → `cf --profile a group create`
  2. `cf --profile a status` → 기기 이름, 에포크 1, 구성원 1명, 릴레이 연결 상태 `connected`
  3. 다시 `status` 실행해도 같은 device_id 앞자리

## F06. 페어링 (CLI)

- **목표**: 두 번째 프로필이 초대 코드로 그룹에 들어온다. SAS로 확인한다.
- **선행**: F05
- **범위**: `core/src/pairing` (03-protocol 4절 전체), 초대 QR 문자열·텍스트 코드 생성/파싱, CLI `cf invite`(텍스트 코드 + 터미널 QR 출력, 승인 대기), `cf join <코드>`, 두 번째 Hello 시 초대 무효화
- **범위 밖**: 기기 제거, GUI
- **완료 조건**
  - [ ] 정상 페어링 후 두 프로필의 로스터가 같음
  - [ ] 실패 테스트: 만료된 초대, 이미 사용한 초대, 오타 코드(체크 실패), 거절, 두 번째 참여 시도
  - [ ] 코드 입력 보정(대소문자, `O→0`, 하이픈/공백) 테스트
  - [ ] 03-protocol 4절 `(초안)` 제거
- **사용자 확인 방법**
  1. 터미널 A: `cf --profile a invite` → 코드와 QR이 뜨고 대기
  2. 터미널 B: `cf --profile b init --name phone-sim` → `cf --profile b join <코드>`
  3. 기대 결과: 양쪽에 같은 6자리 숫자, A에서 `y` 입력 → B에 `joined`
  4. `cf --profile a status`, `cf --profile b status` → 둘 다 구성원 2명

## F07. 텍스트 송수신 (CLI)

- **목표**: 페어링된 기기끼리 암호화된 텍스트가 오간다.
- **선행**: F06
- **범위**: 공개 API `send_text`, `EventSink::on_clip`, CLI `cf send <텍스트>`(또는 stdin), `cf listen`(받은 내용 출력), 크기 제한 1 MiB
- **범위 밖**: 이미지, 클립보드 연동
- **완료 조건**
  - [ ] 3개 프로필 그룹에서 한 곳이 보내면 나머지 둘이 받음 (통합 테스트)
  - [ ] 그룹 밖 프로필(다른 그룹)은 못 받음
  - [ ] 릴레이가 보는 바이트에 평문이 없음을 확인하는 테스트(릴레이 쪽 수신 바이트에서 평문 검색)
  - [ ] 한글·이모지·1 MiB 경계 테스트
- **사용자 확인 방법**
  1. 터미널 B: `cf --profile b listen`
  2. 터미널 A: `cf --profile a send "안녕 clip-ferry"`
  3. 기대 결과: B에 `[laptop] 안녕 clip-ferry`
  4. 릴레이 로그에는 바이트 수 집계만 있고 내용이 없음

## F08. 기기 관리: 목록 · 이름 변경 · 제거 · 키 회전 · 복구

- **목표**: 기기를 제거하면 제거된 기기는 더 이상 못 받고, 꺼져 있던 기기는 돌아와서 따라잡는다.
- **선행**: F07
- **범위**: 03-protocol 3절 전체 (RosterUpdate 충돌 해소, Rekey, 이전 에포크 30일 유예, EpochQuery), CLI `cf devices`, `cf rename <이름>`, `cf remove <기기 이름 또는 id 앞자리>`
- **범위 밖**: GUI
- **완료 조건**
  - [ ] 제거 후 제거된 기기가 새 메시지를 못 받는 테스트
  - [ ] 제거 시점에 오프라인이던 남은 기기가 재접속 후 EpochQuery로 따라잡는 테스트
  - [ ] 동시 RosterUpdate 충돌이 모든 기기에서 같은 결과로 수렴하는 테스트
  - [ ] 유예 기간 경과 시 "다시 페어링" 상태가 되는 테스트(시계 주입)
  - [ ] 03-protocol 3절 `(초안)` 제거
- **사용자 확인 방법**
  1. 프로필 a, b, c를 한 그룹으로 페어링 (F06 절차 두 번)
  2. c의 `listen`을 끈 상태에서 `cf --profile a remove phone-sim` (b 제거)
  3. b와 c에서 `listen` 실행 → a에서 `send "after remove"`
  4. 기대 결과: c는 받음(재접속 직후 따라잡기), b는 못 받고 `removed or stale` 상태 표시
  5. `cf --profile a devices` → 2대, 에포크 2

## F09. 데스크톱 셸 기본 (Tauri 트레이)

- **목표**: 트레이에 상주하고 코어에 연결된 앱이 Windows·macOS에서 실행된다.
- **선행**: F08
- **범위**: `apps/desktop`(Tauri 2, React+TS+Vite), 트레이 아이콘(연결 상태 색), 메뉴(열기/종료), 작은 메인 창(상태·기기 이름), `keyring` 기반 `SecretStore`, 코어 이벤트 → UI 전달, 릴레이 주소 설정
- **범위 밖**: 페어링 UI, 클립보드
- **완료 조건**
  - [ ] Windows·macOS 둘 다 `cargo tauri dev`로 실행 (실행 못 한 OS는 보고에 명시)
  - [ ] 창을 닫아도 트레이에 남고, 트레이 메뉴 "종료"로 종료
  - [ ] 릴레이를 껐다 켜면 아이콘 상태가 바뀜
- **사용자 확인 방법**
  1. `cargo run -p clip-ferry-relay -- --listen 0.0.0.0:8787`
  2. `cd apps/desktop && npm install && npm run tauri dev`
  3. 기대 결과: 트레이 아이콘 표시, 창에 `연결됨`. 릴레이 종료 시 `재연결 중`

## F10. 데스크톱 페어링 UI

- **목표**: 데스크톱에서 그룹을 만들고, QR/코드로 다른 기기를 초대하거나 참여한다.
- **선행**: F09
- **범위**: 첫 실행 마법사(기기 이름 → 새 그룹 / 코드로 참여), 초대 화면(QR + 텍스트 코드 + 남은 시간), SAS 확인 대화상자, 참여 화면(코드 붙여넣기)
- **범위 밖**: 기기 제거 UI(F13)
- **완료 조건**
  - [ ] 데스크톱 ↔ CLI 프로필 간 페어링 양방향 (데스크톱이 초대 / CLI가 초대)
  - [ ] 만료·거절·잘못된 코드 시 이해 가능한 한국어 메시지
- **사용자 확인 방법**
  1. 데스크톱 앱 첫 실행 → 이름 입력 → "새 그룹"
  2. "기기 추가" → 표시된 텍스트 코드를 `cf --profile x join <코드>`에 입력
  3. 기대 결과: 앱에 SAS 대화상자, CLI와 같은 숫자 → 승인 → 앱 기기 목록에 2대
  4. 반대로 `cf --profile y invite` 코드를 다른 PC의 앱 "코드로 참여"에 입력

## F11. 텍스트 자동 동기화 (데스크톱)

- **목표**: 데스크톱에서 텍스트를 복사하면 다른 기기 클립보드에 자동으로 들어간다.
- **선행**: F10
- **범위**: Windows `AddClipboardFormatListener`, macOS `changeCount` 500ms 폴링, 받은 텍스트 클립보드 쓰기, **에코 방지**(마지막으로 쓴 내용 해시와 같으면 보내지 않음), **민감 클립보드 제외**(02-architecture), 짧은 시간 연속 복사 디바운스(300ms)
- **범위 밖**: 이미지
- **완료 조건**
  - [ ] PC A 복사 → PC B 붙여넣기 가능, 반대 방향도
  - [ ] 받은 내용이 다시 되돌아가 무한 반복되지 않음
  - [x] 민감 표시가 붙은 복사(비밀번호 관리자 등)의 처리는 설정(`sync_sensitive`)을 따른다. **기본은 동기화함**(모바일↔데스크톱 비밀번호 옮기기를 지원, 2026-10-31 사용자 결정). 끄면 읽지도 보내지도 않는다. 설정 화면은 F13
  - [ ] 셸 코드에 감지·쓰기 외 로직 없음
- **사용자 확인 방법**
  1. 두 대의 PC(또는 PC 1대 앱 + CLI `listen`)를 페어링
  2. A에서 메모장 텍스트 복사 → B에서 Ctrl/Cmd+V
  3. 기대 결과: 1초 이내 붙여넣기 됨. B에서 다른 텍스트 복사 → A에서 붙여넣기 됨

  - [ ] 노드 1에 붙은 CLI → 노드 2에 붙은 CLI 전달 통합 테스트
  - [ ] NATS JetStream(영속) 미사용 확인
- **사용자 확인 방법**: `docker compose -f deploy/compose.multi.yml up` → `cf --relay ws://localhost:8787` 와 `--relay ws://localhost:8788` 로 각각 붙은 두 프로필 간 `send`/`listen`

## F27. 관측과 남용 방지 강화

- **목표**: 운영자가 서버 상태를 보고, 남용을 막는다. 내용은 여전히 모른다.
- **선행**: F26
- **범위**: Prometheus 메트릭(연결 수, 프레임/바이트 처리량, 에러 코드별 수, 푸시 성공/실패), 제한값 설정화, 푸시 남용 제한(연결당 분당 푸시 수), Grafana 대시보드 JSON
- **완료 조건**
  - [ ] 메트릭 레이블에 채널 ID·태그·IP가 없음
- **사용자 확인 방법**: `curl localhost:9090/metrics` 출력 확인

# M6. 선택 기능 (필요 시)

- **F28. 같은 네트워크 직접 연결**: mDNS로 같은 LAN 기기를 찾아 릴레이 없이 전송(이미지 대역폭 절감). 같은 봉투 형식 사용.
- **F29. 로컬 클립보드 내역**: 기기 로컬에만, 암호화된 저장, 개수·기간 제한, 지우기.
- **F30. 받을 기기 지정 전송**: 기본 전체, 설정이나 트레이 메뉴로 특정 기기만(`Publish.to`).
- **F31. 데스크톱 배포 패키지**: Windows 코드 서명, macOS 공증, 자동 업데이트(Tauri updater).

선택 기능은 착수 전에 사용자와 범위·완료 조건을 다시 합의하고 이 문서에 상세 항목을 추가한다.
