# F14. 릴레이 배포 (1단계: 라즈베리파이 + Tailscale) — 해야 할 것과 확인할 것

상태: `진행중` (docs/05-progress.md). 브랜치 `f14-relay-deploy`, 푸시됨.

## 먼저 알아둘 것

- **범위가 줄었다.** 클라우드 배포 대신 집 Pi 5에 먼저 올려 시험한다(D-014). 클라우드·인증서·프록시 IP 처리는 이후 단계다.
- 릴레이는 Docker로 Pi(arm64)에 올리고, **Tailscale IP에만** 포트를 연다. 접속 주소는 `ws://<Pi의 Tailscale IP>:8787` (Pi는 `100.84.191.27`).
- `ws://`(평문)지만 Tailscale 구간은 WireGuard로 암호화되고, 클립보드 내용은 종단간 암호화다.
- `wss://`는 **서버 인증서가 있어야** 한다. 클라이언트(앱·CLI)는 이미 `wss://`를 지원하지만 실제 TLS 서버와는 아직 접속해 보지 않았다.
- 로컬 검증은 통과했다: fmt, clippy, `cargo test --workspace`, Docker 이미지 빌드(PC x86_64, 42 MB), 읽기 전용 루트 + `cap-drop ALL`로 컨테이너 기동과 `/healthz` 응답. **Pi(arm64) 빌드는 Pi에서 처음 확인한다.**

## 1. Pi에 올리기 (사용자)

```bash
git clone https://github.com/toddla23/clip-ferry.git
cd clip-ferry
git checkout f14-relay-deploy
echo "CF_BIND=$(tailscale ip -4)" > deploy/.env
docker compose -f deploy/compose.yml up -d --build
```

- [ ] 빌드가 끝까지 성공한다(Pi 5에서 몇 분). 실패하면 출력을 그대로 알려 준다.
- [ ] `docker compose -f deploy/compose.yml ps`에 relay가 `running`
- [ ] Pi에서 `curl http://$(tailscale ip -4):8787/healthz` → `ok`
- [ ] 로그에 `listening on 0.0.0.0:8787`: `docker compose -f deploy/compose.yml logs --tail 5`

## 2. PC에서 Pi 릴레이로 접속 (사용자)

- [ ] PowerShell: `curl.exe http://100.84.191.27:8787/healthz` → `ok`
- [ ] 같은 Wi-Fi가 아닌 곳(폰 핫스팟 등)에서도 되는지 — 서로 다른 네트워크 확인 (PC가 핫스팟에 붙은 상태에서 같은 `curl.exe`)
- [ ] Pi를 LAN의 다른 IP로 접속하면 **안 열려야** 한다(Tailscale IP에만 바인드): `curl http://<Pi의 집 LAN IP>:8787/healthz` → 연결 거부

## 3. 앱·CLI로 동기화 시험 (사용자)

- [ ] 데스크톱 앱 릴레이 주소를 `ws://100.84.191.27:8787`로 바꾸고 `연결됨`이 뜬다 (창의 릴레이 주소 설정, 또는 `CF_RELAY` 환경 변수)
- [ ] 릴레이가 PC에서 돌던 이전 상태와 달라진 점: **기기 채널이 같아서 기존 페어링은 그대로 쓸 수 있다.** CLI도 같은 주소로 맞춘다: `cargo run -q -p clip-ferry-cli -- --profile x --relay ws://100.84.191.27:8787 listen`
- [ ] 텍스트 양방향 동기화(앱 ↔ CLI)
- [ ] 이미지 동기화(5 MB 스크린샷) — F12와 같은 시나리오
- [ ] Pi 릴레이 로그에 바이트 수 집계만 있고 내용·채널 ID가 없다: `docker compose -f deploy/compose.yml logs --tail 20`
- [ ] 릴레이를 껐다 켜면 앱이 `재연결 중` → `연결됨`: `docker compose -f deploy/compose.yml restart`

## 4. 운영 확인 (사용자)

- [ ] **Pi 재부팅 후 자동으로 뜬다**(`restart: unless-stopped`, `deploy/.env`로 `CF_BIND` 고정): `sudo reboot` 뒤 `curl`이 `ok`
- [ ] 릴레이 컨테이너가 파일을 쓰지 않는다: `docker diff $(docker compose -f deploy/compose.yml ps -q relay)` → 비어 있음

## 이후 단계 (F14 안에서 하지 않음)

| 항목 | 내용 | 언제 |
|---|---|---|
| Tailscale 인증서 | 관리 콘솔에서 HTTPS 인증서를 켜고 Pi에서 `tailscale cert`로 발급. 무료, 도메인 불필요 | 모바일 시험(F15) 전 |
| `wss://` 종단 | 인증서를 쓰는 TLS 종단(`tailscale serve` 등)을 릴레이 앞에 둔다. 클라이언트는 이미 지원, 실제 TLS 접속은 이때 처음 확인 | 인증서 발급 후 |
| 프록시 뒤 클라이언트 IP | 프록시 뒤에서는 모든 연결이 프록시 IP로 보여 IP당 32개 제한을 공유한다. 프록시 헤더를 신뢰하는 옵션 필요 | `wss://` 종단 도입 때 |
| 클라우드 배포 | Fly.io 등. 같은 `deploy/Dockerfile` 사용. 호스팅·도메인·번들 ID 결정 필요(O-03, O-04) | 개인 시험 후 |
| 모바일 평문 제한 | Android·iOS는 평문 `ws://`를 막는 경우가 많다 | F15 |
| 기본 릴레이 주소 | 앱 기본값은 아직 개발용(`ws://127.0.0.1:8787`). 정식 주소가 정해지면 바꾼다 | 클라우드 배포 때 |
| macOS | F09~F13과 함께 미확인 | Mac이 생길 때 |
