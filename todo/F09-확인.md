# F09. 데스크톱 셸 기본 (Tauri 트레이) — 확인할 것

상태: `확인대기` (docs/05-progress.md)

## 먼저 알아둘 것

- **처음 실행하면 기기와 그룹을 자동으로 만든다.** 이름은 컴퓨터 이름(`COMPUTERNAME`/`HOSTNAME`), 그룹은 구성원 1명. 이름을 정하고 "새 그룹 / 코드로 참여"를 고르는 마법사는 F10에서 만든다. 그 전까지의 임시 동작이다.
- 비밀(기기 키·그룹 키·로컬 저장 키)은 **Windows Credential Manager**에 저장된다(`keyring`). 상태 파일은 `%APPDATA%\app.clipferry.desktop\state.bin`, 설정은 같은 폴더의 `settings.json`.
- **macOS에서는 실행해 보지 못했다.** 코드는 `keyring`의 Keychain 백엔드와 Tauri 트레이를 쓰도록 되어 있고 CI(macOS)에서 빌드·테스트는 돈다. 직접 실행은 Mac이 있을 때 확인해야 한다.
- 번들 ID `app.clipferry.desktop`은 임시값이다(O-03 미정).
- 앱 아이콘은 임시로 직접 그린 파란 사각형 + 화살표다. 트레이 아이콘은 코드에서 색 원을 그린다(연결됨 초록 / 재연결 중 주황 / 끊김 회색 / 제거됨·중지 빨강).
- 클립보드는 아직 다루지 않는다(F11). 받은 텍스트는 버린다.
- **빌드 순서가 바뀌었다.** Tauri 매크로가 컴파일할 때 `apps/desktop/dist`를 읽으므로, 새로 받은 저장소에서는 `cargo`를 돌리기 전에 한 번 `cd apps/desktop && npm ci && npm run build`가 필요하다. CI에도 이 단계를 넣었다(Linux는 WebKitGTK 등 시스템 패키지 설치도 추가).

## 직접 확인할 것 (PowerShell)

사전 준비: 이전에 띄운 `clip-ferry-relay`가 남아 있으면 닫는다. **먼저 UI를 한 번 빌드한다**(처음 한 번만): `cd apps\desktop; npm install; npm run build`

1. 터미널 1: `cargo run -p clip-ferry-relay -- --listen 127.0.0.1:8787`
2. 터미널 2: `cd apps\desktop; npm run tauri dev` (처음에는 Rust 컴파일로 몇 분 걸린다)

- [x] 작업 표시줄 오른쪽 트레이(숨겨진 아이콘 ^ 안일 수 있음)에 **초록 원** 아이콘이 보이고, 마우스를 올리면 `clip-ferry — 연결됨`
- [x] 창에 `연결됨`, 기기 이름(컴퓨터 이름), 기기 ID 8자리, `에포크 1 · 구성원 1명`
- [x] 터미널 1에서 Ctrl+C → 창이 `재연결 중`, 트레이 아이콘이 **주황**. 릴레이를 다시 켜면 `연결됨`·초록으로 돌아온다 (재연결 간격이 최대 60초라 잠깐 걸릴 수 있다)
- [x] 창의 X 버튼 → 창만 사라지고 트레이에 남는다. 트레이 아이콘 왼쪽 클릭 또는 우클릭 → `열기` → 창이 다시 뜬다
- [x] 트레이 우클릭 → `종료` → 앱이 완전히 끝난다 (터미널 2의 `tauri dev`도 끝남)
- [x] 릴레이 주소 칸에 `ws://127.0.0.1:9999` 입력 → `저장` → `재연결 중`(그 주소엔 릴레이가 없으므로). 다시 `ws://127.0.0.1:8787`로 저장 → `연결됨`. 잘못된 값(`http://x`)은 오류 문구
- [x] 앱을 종료했다 다시 켜도 기기 ID가 같고 저장한 릴레이 주소가 유지된다

처음 상태로 되돌리려면(선택): 앱 종료 후 `Remove-Item -Recurse $env:APPDATA\app.clipferry.desktop` 와 `cmdkey /delete:device_keys.clip-ferry`, `state_key.clip-ferry`, `group_key/1.clip-ferry` (`cmdkey /list | Select-String clip-ferry`로 목록 확인). 한쪽만 지우면 코어가 "한쪽만 남아 있다"며 열기를 거부한다.

> 2026-10-31 사용자가 직접 확인하다 "릴레이 주소 저장 후 `재연결 중`에 머무는" 문제를 발견 → 원인은 `저장` 응답(오래된 상태)이 먼저 도착한 `연결됨` 이벤트를 덮어쓰는 UI 경쟁 상태. 상태에 `seq`를 붙여 오래된 것을 버리도록 수정, CDP로 실제 UI를 15회 반복해 모두 `연결됨` 확인 후 사용자 재확인 완료.

## 참고

- 구조: `apps/desktop/ui`(React: 상태 표시·릴레이 주소) / `apps/desktop/src-tauri/src`(`shell` 코어 연결, `tray` 트레이, `secrets` Credential Manager·Keychain, `settings` 릴레이 주소 파일, `view` 화면용 요약).
- 창 ↔ 코어: 창이 `get_view`/`set_relay_url` 명령을 부르고, 상태가 바뀔 때마다 앱이 `view-changed` 이벤트를 보낸다. 화면용 요약에는 기기 ID 앞 4바이트까지만 있고 비밀은 없다.
- 릴레이 주소 기본값은 `ws://127.0.0.1:8787`. 저장된 설정이 없으면 환경 변수 `CF_RELAY`를 따른다. `wss://`는 형식만 통과시키며 실제 연결은 F14에서 가능해진다(코어가 아직 `ws://`만 지원).
- 이 앱은 한 컴퓨터에 하나만 띄운다는 전제다(같은 키 저장소·상태 파일을 쓴다). 중복 실행 방지는 아직 없다.
