# F14b. 릴레이 공개 배포 (`wss://`) — 확인할 것

상태: `확인대기` (docs/05-progress.md). 브랜치 `f14b-wss-deploy` (F14 브랜치 위).

**확인 결과 (2026-11-02, 사용자 보고)**: 1~4번 통과. Pi 빌드·기동, `tailscale serve`로 `https://` 인증서 경고 없이 응답, 예전 평문 `ws://100.84.191.27:8787` 차단, 앱·CLI가 `wss://`로 연결되어 텍스트·이미지 양방향 동기화, Pi 로그에 집계 숫자만(내용·헤더·이메일 없음), `docker diff` 비어 있음. 5번 재부팅 후에도 컨테이너와 `tailscale serve`가 복구되어 `ok`(사용자 보고).

## 먼저 알아둘 것

- 릴레이는 그대로 평문으로 받고, **`tailscale serve`가 TLS를 맡는다.** 인증서(Let's Encrypt)는 Tailscale이 발급·갱신하므로 도메인도 비용도 필요 없다.
- 접속 주소는 `wss://raspberry-pi.tailb6b7a3.ts.net` (포트 없음). tailnet 안에서만 열린다.
- 릴레이에 `--trust-proxy` 옵션(`CF_RELAY_TRUST_PROXY`)을 추가했다. 켜면 루프백·사설 주소에서 직접 온 연결에 한해 `X-Forwarded-For`로 IP당 연결 제한을 기기별로 센다. 값이 여러 개면 가장 오른쪽을 쓴다.
- 이미 확인한 것: Pi에서 `tailscale serve`가 `X-Forwarded-For: <기기 Tailscale IP>`를 붙인다. 계정 이메일 등 `Tailscale-User-*` 헤더도 붙이지만 릴레이는 읽지도 로그에 남기지도 않는다. PC에서 HTTPS 인증서가 경고 없이 신뢰됨(2026-11-02).
- 로컬 검증: fmt, clippy, `cargo test --workspace` 통과(릴레이 단위 6 + 통합 2 추가).
- **앱 기본 릴레이 주소는 바꾸지 않았다.** 개인 tailnet 주소를 공개 저장소의 기본값으로 넣을 수 없어서, 정식 주소(도메인·클라우드, O-03·O-04)가 정해질 때 바꾼다.

## 직접 확인할 것

### 1. Pi 릴레이를 새 코드로 올리기 (Pi)

```bash
cd ~/clip-ferry
git fetch && git checkout f14b-wss-deploy && git pull
printf 'CF_BIND=127.0.0.1\nCF_TRUST_PROXY=true\n' > deploy/.env
docker compose -f deploy/compose.yml up -d --build
sudo tailscale serve --bg --https=443 http://127.0.0.1:8787
tailscale serve status
```

- [x] 빌드 성공, `docker compose -f deploy/compose.yml ps`가 `127.0.0.1:8787->8787/tcp`로 running
- [x] `tailscale serve status`에 `https://raspberry-pi.tailb6b7a3.ts.net` → `proxy http://127.0.0.1:8787`
- [x] 이전의 임시 시험 설정이 남아 있으면 지운다: `sudo tailscale serve --https=8443 off`

### 2. TLS 확인 (PC, PowerShell)

```powershell
curl.exe -v https://raspberry-pi.tailb6b7a3.ts.net/healthz
```

- [x] 인증서 경고 없이 `ok`
- [x] 예전 `ws://100.84.191.27:8787`은 이제 열리지 않는다(릴레이를 127.0.0.1에만 열었으므로): `curl.exe http://100.84.191.27:8787/healthz` → 연결 거부

### 3. `wss://`로 동기화 (PC)

앱·CLI 모두 `wss://raspberry-pi.tailb6b7a3.ts.net`를 쓴다. 앱·CLI 프로필이 없으면 F14와 같은 순서로 새로 만든다(`todo/F14-확인.md` 3번).

```powershell
cd C:\Users\jonghyeok\Documents\clip-ferry
$env:CF_RELAY = "wss://raspberry-pi.tailb6b7a3.ts.net"
cd apps\desktop
npm run tauri dev
```

- [x] 앱 창에 `연결됨` (**실제 TLS 서버와의 `wss://` 접속, 클라이언트로는 처음**)
- [x] CLI: `cargo run -q -p clip-ferry-cli -- --profile x --relay wss://raspberry-pi.tailb6b7a3.ts.net listen` 이 `connected`
- [x] 앱 ↔ CLI 텍스트·이미지 양방향 동기화

### 4. IP당 제한이 기기별로 세어지는지 (Pi)

- [x] 릴레이 로그에 연결 수가 보이고 기기마다 따로 센다. 간단 확인: 앱과 CLI를 동시에 연결해도 `연결이 거절되지 않는다`(예전에는 둘 다 `127.0.0.1`로 합쳐져 한도를 나눠 썼다)
- [x] 로그에 이메일·헤더·채널 ID가 없다 (집계 숫자만): `docker compose -f deploy/compose.yml logs --tail 20`
- [x] 컨테이너가 파일을 쓰지 않는다: `docker diff $(docker compose -f deploy/compose.yml ps -q relay)` → 비어 있음
- [ ] (선택) 프록시 뒤 기기별 제한을 직접 보려면 Pi의 `deploy/.env`에 `CF_RELAY_MAX_CONNS_PER_IP=1`을 넣어 앱+CLI를 같이 붙여 본다. 통합 테스트로는 이미 검증됨

### 5. 재부팅 (Pi)

- [x] `sudo reboot` 뒤 `curl.exe -v https://raspberry-pi.tailb6b7a3.ts.net/healthz` → `ok` (컨테이너와 `tailscale serve`가 자동으로 복구)

## 정리

```powershell
Remove-Item Env:CF_RELAY -ErrorAction SilentlyContinue
```
